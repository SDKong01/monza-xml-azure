# ADR-003: Removal of NGINX Gateway for Multi-Product Routing

- **Status:** Accepted  
- **Date:** 2025-08-31  
- **Deciders:** Orchestrator, Backend Architect  

## Context and Problem Statement
Originally, NGINX was introduced as a central gateway to perform host-based routing for multiple products (SENNA and KIMBALL) hosted behind a single Application Load Balancer (ALB).  
With the migration to **AWS App Runner** for serving applications and an **ALB dedicated to Keycloak** on EC2, the need for a custom NGINX gateway is questioned. App Runner already provides a fully managed ingress layer with HTTPS termination, scaling, and custom domain mapping, while the ALB secures Keycloak separately. The team must decide whether to maintain or remove NGINX from the architecture.  

## Considered Options
- **Option 1:** Keep NGINX as the central gateway for host-based routing.  
- **Option 2:** Remove NGINX, use App Runner’s managed gateway for apps and ALB for Keycloak.  

## Decision Outcome
**Chosen Option:** Option 2 — Remove NGINX, because App Runner provides its own managed ingress with TLS, scaling, and routing, and ALB already secures Keycloak. Maintaining NGINX adds unnecessary complexity, cost, and operational overhead without providing meaningful value in this new architecture.  

### Positive Consequences
- Reduced operational complexity (no custom gateway to manage or scale).  
- Lower infrastructure cost (no EC2 instances running NGINX).  
- Simpler architecture with clear separation of concerns (App Runner for apps, ALB for Keycloak).  
- Leverages AWS-managed services for scaling, certificates, and reliability.  

### Negative Consequences
- Loss of advanced request manipulation capabilities (rewrites, custom headers, fine-grained rate limiting) that NGINX could provide.  
- Any future need for centralized path-based routing would require adding CloudFront, API Gateway, or reintroducing a gateway.
